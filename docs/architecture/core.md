# Boomdrive rules

The rules that bind wherever a change is made in this repository,
written so a reviewer can point at a diff and say which rule it breaks.
The runner is the thin part on each host: it keeps the clones and views
of the repositories its configuration names, and turns the control
plane's work into `flume launch` calls, carrying their results back.
Every decision about what work there is, where it runs and how it is
carried through is the control plane's or flume's. There are no area
pages yet; a rule that binds only one part of the tree moves to an area
page when that part exists.

## Rules

### What the runner decides

- **[core.1]** The runner decides nothing the control plane or flume decides: it starts work only as a `flume launch` or a tool command the control plane asked for, and reports each tool's results as the tool gave them.
- **[core.5]** The runner keeps a clone or a view only of a repository its configuration names, and keeps none of one it does not; the configuration names the repositories and where their views go, and no stream or kind.
- **[core.43]** Where its configuration asks for them, the runner keeps one VS Code workspace for each owner of its kept repositories, beside the owner's views, whose `folders` are exactly that owner's kept repositories, set at every pass, and keeps everything else in the file as it was; where the configuration does not ask, it writes and removes none.
- **[core.13]** The runner starts, keeps and stops no tool's long-running process and runs no tool's housekeeping of its own accord: sluice's driver, the multiplexer's server and any settle loop are the host's service manager's.
- **[core.14]** The runner's clone of a repository is the host's one clone of it: Flume, sluice and what a launch runs may work in its container, and the runner alone fetches it and moves its default branch and its view, and never removes, moves or rewrites a ref, worktree or file another tool made there.
- **[core.15]** The runner passes a launch as its control plane gave it and asks no other tool anything for it: what a unit works under is Flume's to ask Boom at the launch.
- **[core.16]** Every command the runner carries runs one tool's own command line once, under its lease, its answer carried as the tool gave it, or is one of the runner's own, drain, resume, upgrade or setup; no command adds a repository for the host to keep.

### Configuration and setup

- **[core.17]** The runner is configured by its configuration alone, which a person can write by hand, and does nothing under a control plane that a configuration written by hand could not ask of it; a hosted control plane writes the configuration's managed level for the user, and what that level holds wins over the host's own.
- **[core.18]** Setup configures a host only through each tool's own command line, the runner's own included, and never by writing a tool's files.

### The control plane

- **[core.2]** The control plane is reached through exactly one interface, and an implementation of it, crew's state repository or a hosted control plane, implements that interface and nothing of the runner's own; no code outside an implementation names crew, its records or the hosted control plane's protocol.
- **[core.3]** No connection comes in to a host: the runner opens no listening socket and every connection it makes is outgoing.
- **[core.19]** A runner serves the one control plane its `[control_plane]` `type` names, and every partition it serves is that control plane's.
- **[core.20]** A command given on the host reaches a running runner only through a file in its data directory, read at its next pass, and no command connects to the runner.
- **[core.21]** The runner keeps its socket to a hosted control plane alive with the WebSocket protocol's own pings, and after every reconnect sends its whole hello and resends, each under its own id, what the control plane has not acknowledged.
- **[core.22]** A control plane that cannot be reached is tried again on a bounded backoff with jitter, from seconds up to `poll_interval`, and never pass after pass.
- **[core.23]** The runner raises no alarm of its own about its reach: it says one line when its control plane becomes unreachable and one when it returns, and its presence is the control plane's to show.
- **[core.42]** The runner's protocol with a hosted control plane is JSON Schema in the hosted implementation's crate, one directory per version, whose messages carry the interface's shapes; every object it names is closed, so a message holds only what its version names; each end checks every message it is sent against that version before reading it, and refuses a failing one whole; and a version a release of the runner has spoken is never changed or removed, a change to it being a new version.

### Work under a lease

- **[core.9]** The runner takes the control plane's work only under a lease it was offered, and takes a launch only while it keeps the launch's repository and the Flume stream the launch runs in has room on its host, as Flume's status gives it; it names a stream only where the launch names one.
- **[core.10]** Every report about leased work names the lease's number, and the runner carries out each act and command once, across restarts; once the control plane refuses a report for a lease the runner no longer holds, the runner neither acts on that work nor reports it again, and removes nothing of it.
- **[core.24]** An offer whose lease has expired by the runner's clock is not launched, acted on or claimed until a pull gives it again under a live lease.
- **[core.25]** A pass whose report cannot be saved carries out no further act or command that pass.

### What goes back

- **[core.11]** What the runner carries back of a tool is the tool's own answer, each field as the tool gave it, or a reference to it: no repository content, task log, raw material or terminal byte is carried in a report, written to the runner's data or its log, or kept.
- **[core.26]** What goes over one partition's connection names only that partition's own repositories, leases, places and commands.
- **[core.27]** To a hosted control plane, the runner carries of a tool's status only the fields the protocol's copy of it names, each as the tool printed it, and leaves out the rest.
- **[core.28]** Nothing leaves a host from the runner but its control plane's protocol, git's calls and an OTLP export to a collector the host's configuration names, and what goes as health holds only ids, names, statuses, times, counts and digests.

### Terminals

- **[core.29]** The runner reaches an agent's terminal only through Flume's command line, and no code of the runner's names a multiplexer or runs one's command line.
- **[core.30]** A terminal leaves the host only encrypted end to end to the browser that opened it: the runner makes a key pair for each terminal and signs its share with the host's key, takes the browser's share only when a key certified to a member signed it, and never sends a pane's bytes in the clear.

### Identity and credentials

- **[core.4]** No token, key or credential is in the repository: none is committed, none is a default in code, configuration or tests, and the runner reads each from the host when it runs.
- **[core.31]** A host's identity with a hosted control plane is a key pair the runner makes on the host, whose private key never leaves it, and every connection proves the key is held.
- **[core.32]** The host's key is kept only in the host's own credential store, the macOS keychain or an encrypted systemd credential, and never in a file readable in the clear.
- **[core.33]** Under a hosted control plane, no forge App's key or id is on a host for the runner or a tool to mint with: a host's forge calls use short-lived tokens the control plane sends down the runner's own connection, each for a repository of a drive the host serves.
- **[core.34]** The runner changes a repository only through the host's own `git` command, and a library may only read.

### The runner's own files

- **[core.35]** The data directory holds only the lock, the clones, the runner's report, a launch's brief while Flume reads it and each implementation's caches, and everything in it but the report is made again from origin, Flume and the control plane.
- **[core.36]** A release never drops, renames or changes the meaning of a field the release before it reads in a file the runner keeps, and a file the runner cannot read makes it refuse to start.

### Releases and installs

- **[core.37]** An install or an upgrade runs a release of the runner, or of a tool it brings, only once it has verified the release's provenance against the identity of the workflow that built it, and a failed check keeps what runs.
- **[core.38]** Each release names the least version of each tool it runs with and the versions it was checked against, and below a floor the runner takes no work that needs the tool and keeps its repositories.

### Output

- **[core.39]** Every command of the runner's that answers takes `--json`, whose form within a version only ever gains fields; a refusal is `{"refused":{"refusal":{"reason":…}}}` on standard output; and it exits 0 answered, 1 refused and 2 for a usage error or a host that must be fixed.
- **[core.40]** Each line the running runner writes starts with its time, RFC 3339 in UTC to the second, then its subject and its words.

### Names

- **[core.12]** Every configuration key and every type names what it holds to its reader: a duration's key ends in `_interval`, a path's in `_root`, `_dir` or `_file`, and no key or type takes a word another tool uses for something else.

### The repository

- **[core.6]** Nothing commercial, no pricing, tier or customer, appears in this repository.
- **[core.41]** No text of a private repository is copied into this one, and no host, partition, state repository, person's path or account of anyone's is in its code, tests, fixtures or docs.

### The gate

- **[core.7]** Every file the tree tracks is owned by a formatter the gate runs, or is excluded by name with its reason; every crate is a moon project of its own, listed in `.moon/workspace.yml` with its language declared, whose check-fast tasks format, lint, type-check and test it, one task per check.
- **[core.8]** Every tool a gate task runs is the version the tree pins, on every host that runs the gate.

## Details

- **core.1** Rules out: the runner choosing which work runs, on which host, in what order or under which kind; a `flume launch` or a tool command with no ask of the control plane behind it; a result rewritten, summarised or judged before it is carried back; the runner deciding a stage, a submission or a landing that flume decides, or a branch's making that sluice decides. Not ruled out: refusing work for a repository its configuration does not name, and saying so to the control plane (core.5); leaving work untaken while its stream has no room (core.9); a launch or an act that a control plane's implementation gives because it read the control plane's own rule from the control plane's own records, as crew's implementation reads when a role is wanted (core.2); the runner's own commands, drain, resume, upgrade and setup (core.16). Source: record 0001; record 0002; record 0008; the user, 2026-10-31 and 2026-11-01; boomdrive-cloud record 0017.
- **core.5** Rules out: a clone made because work named a repository the configuration does not; a dropped repository's clone or view fetched, moved or made again, or left once neither holds work the forge lacks; a stream, a kind or a drive named in the configuration, in the runner's own keys or a control plane's table; a kinds file, a kind's source or a lock named there or passed to Flume by the runner, since where a host's kinds come from is its Flume configuration's; a repository added to the configuration because work named it. Not ruled out: a dropped repository's clone and view left untouched and named while either holds work the forge lacks (crew record 0052 part 2); the repositories kept reported to the control plane as the host's capacity, which registers none of them to a drive (boomdrive-cloud record 0007); a launch's kind passed to Flume as its control plane gave it, by its name or its identity `<source>/<name>@<version>` (flume record 0022); the configuration's managed level written by setup with the repositories of the drives the host serves, a repository leaving it when no such drive holds it (record 0009). Source: the user, 2026-10-31, in this rule and in the brief of the change the-runner-keeps-its-repositories; record 0002; the user, 2026-11-01, reviewing the change the-runner-carries-crews-work-into-flume ("Kinds are flume's concern, not the runner's or a control plane's"); record 0009; boomdrive-cloud records 0003 and 0007, and its ledger item 3.b; record 0016, which names a customer's unit a drive.
- **core.43** Rules out: a workspace naming a repository the configuration does not keep, or missing one it keeps; a workspace gathered or named by a stream, a kind or a drive (core.5); a person's settings, extensions or tasks in the file dropped or rewritten; a file the runner cannot read as a JSON object, or a link or a folder at the workspace's path, rewritten; a workspace written, or one there removed, while the configuration does not ask for them; a workspace in a view, a clone's container or the data directory (core.14, core.35). Not ruled out: `folders` a person edited set back at the next pass; a workspace no kept owner has there removed with its owner's folder, once the runner has removed the folder's last view and nothing else is left in it; a person's own workspace anywhere else. Source: the user, 2026-11-04 ("I don't know if we should build it as a feature into Boom Drive, where we automatically generate VS Code workspaces that point to your view. Not ruled out: a tool's own command a control plane asked for, run once and awaited (core.16); the runner's own process, kept by the host's service manager. Source: record 0003.
