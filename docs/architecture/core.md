# Boomdrive rules

The rules that bind wherever a change is made in this repository,
written so a reviewer can point at a diff and say which rule it breaks.
The runner is the thin part on each host: it keeps the clones and views
of the repositories its configuration names, and turns the control
plane's work into `flume launch` calls, carrying their results back.
Every decision about what work there is, where it runs and how it is
carried through is the control plane's or flume's. One area page binds
a part of the tree beside these rules: `site.md`, the site's, binding
`site/` and the workflow that publishes it. A rule that binds only one
part of the tree moves to an area page when that part exists.

## Rules

### What the runner decides

- **[core.1]** The runner decides nothing the control plane or flume decides: it starts work only as a `flume launch` or a tool command the control plane asked for, and reports each tool's results as the tool gave them.
- **[core.5]** The runner keeps a clone or a view only of a repository its configuration names, and keeps none of one it does not; the configuration names its accounts, each account's drives, each drive's repositories and where their views go, and no stream or kind. (Record 0028, accepted 2026-11-07.)
- **[core.43]** Where its configuration asks for them, the runner keeps one VS Code workspace for each drive of its configuration, at the repository root under the drive's name, whose `folders` are exactly that drive's kept repositories, set at every pass, and keeps everything else in the file as it was; where the configuration does not ask, it writes and removes none. (Records 0017 as revised and 0028, accepted 2026-11-07.)
- **[core.13]** The runner starts, keeps and stops no tool's long-running process, and runs no tool's housekeeping of its own accord but one: each of its passes, keeping or a part's control pass, ends with Flume's settle of every place, `flume settle --every <bound>`, run once and awaited on that pass's thread, or shares one under way, which keeps Flume's watch over the host while the runner runs (Flume 208; record 0029 as amended on 2026-11-08). The multiplexer's server and a host's own timer of settles are the host's service manager's, and sluice's host process is sluice's own, which its commands start and which ends when idle (sluice 135; sluice record 0093).
- **[core.14]** The runner's clone of a repository is the host's one clone of it: Flume, sluice and what a launch runs may work in its container, and the runner alone fetches it and moves its view; it reads every branch at origin's tracking ref, moves no branch of the clone, whose own ref of a branch sluice keeps is sluice's copy, and never removes, moves or rewrites a ref, worktree or file another tool made there.
- **[core.15]** The runner passes a launch as its control plane gave it and asks no other tool anything for it: what a unit works under is Flume's to ask Boom at the launch.
- **[core.16]** Every command the runner carries runs one tool's own command line once, under its lease, its answer carried as the tool gave it, or is one of the runner's own, drain, resume, upgrade or setup; no command adds a repository for the host to keep.
- **[core.52]** The runner asks no tool to make, move or remove a branch but through Flume's own commands on a place: a branch other places land on is a Flume place's, launched as any launch its control plane gives, landed on its control plane's `land` by Flume's retry of that place's submission (core.53), and made and closed by sluice at Flume's asking; a command for a branch is refused, naming sluice. (Record 0002 as amended on 2026-11-07 and 2026-11-08, accepted by the user on 2026-11-09.)

### Configuration and setup

- **[core.17]** The runner is configured by its configuration alone, which a person can write by hand, and does nothing under a control plane that a configuration written by hand could not ask of it; a hosted control plane writes the configuration's local layer for the user, which sets only the keys the runner lists for it, its repositories adding to the managed layer's, and which the managed layer may pin.
- **[core.18]** A tool's file is written only by that tool's own module, by hand, or by a control plane writing its local layer; the runner writes no other tool's file.

### The control plane

- **[core.2]** The control plane is reached through exactly one interface, and an implementation of it, crew's state repository or a hosted control plane, implements that interface and nothing of the runner's own; no code outside an implementation names crew, its records or the hosted control plane's protocol.
- **[core.3]** No connection comes in to a host: the runner opens no listening socket and every connection it makes is outgoing.
- **[core.19]** A runner serves the one control plane its `[control_plane]` `type` names, and every account it serves is that control plane's.
- **[core.20]** A command given on the host reaches a running runner only through a file in its data directory, read at its next pass, and no command connects to the runner.
- **[core.21]** The runner keeps its socket to a hosted control plane alive with the WebSocket protocol's own pings, and after every reconnect sends its whole hello and resends, each under its own id, what the control plane has not acknowledged.
- **[core.22]** A control plane that cannot be reached is tried again on a bounded backoff with jitter, from seconds up to `poll_interval`, and never pass after pass.
- **[core.23]** The runner raises no alarm of its own about its reach: it says one line when its control plane becomes unreachable and one when it returns, and its presence is the control plane's to show.
- **[core.42]** The runner's protocol with a hosted control plane is JSON Schema in the hosted implementation's crate, one directory per version, whose messages carry the interface's shapes; every object it names is closed, so a message holds only what its version names; each end checks every message it is sent against that version before reading it, and refuses a failing one whole; and a version a release of the runner has spoken is never changed or removed, a change to it being a new version.

### Work under a lease

- **[core.9]** The runner takes the control plane's work only under a lease it was offered, and takes a launch only while it keeps the launch's repository and the Flume stream the launch runs in has room on its host, as Flume's status gives it; it names a stream only where the launch names one.
- **[core.10]** Every report about leased work names the lease's number, and the runner carries out each act and command once, across restarts; once the control plane refuses a report for a lease the runner no longer holds, the runner neither acts on that work nor reports it again, and removes nothing of it.
- **[core.24]** An offer whose lease has expired by the runner's clock is not launched, acted on or claimed until a pull gives it again under a live lease.
- **[core.25]** A pass whose report cannot be saved carries out no further act or command that pass.
- **[core.50]** A pass runs an act's Flume command on its place only once it has answered every offer its pull gives, and, once the next control pass is due, runs none but its first, leaving the rest to that pass; it answers every other want in the control plane's order, so no launch waits behind an act on a place and no answer turns on the order.
- **[core.51]** Before it runs an act's command on a place its pass's listing does not hold, the runner reads Flume's status of that place, which settles nothing; where Flume refuses it, that refusal, as Flume gave it, is the act's answer, and the command is not run.
- **[core.53]** A control plane asks for a work's landing with `land`, an act naming the work's launch and nothing else, under that launch's lease; the runner carries it out as any act, by Flume's retry of the submission of that launch's place, naming no stage and no words, whatever the launch's kind, and Flume's answer is the land's. (Record 0002 as amended on 2026-11-08, accepted by the user on 2026-11-09.)
- **[core.55]** The runner brings up a preview only at its control plane's asking, under the preview's own lease, in a repository it keeps, as sluice's own preview command of the branch at the revision the control plane named, after every launch its pull offers, and once the next control pass is due none after its first; it waits on sluice's bound no longer than its patience, asking again at its next pass; it carries sluice's answer and listing of the preview, each field as sluice printed it, and no output of a command; and on its control plane's done it puts away, by sluice's own release, only a preview it asked sluice for. (Record 0031, accepted by the user on 2026-11-09.)
- **[core.56]** A control plane asks a reader's ends confirmed with `confirm`, an act naming its launch, the one recipient it confirms as and each delivery key, under that launch's lease; the runner carries it out as any act, on the host that holds the launch, by Flume's confirm of exactly those keys as that recipient, once each key is the delivery of an end of the launch's place as Flume's status gives the place, and never as its own name; it confirms no end of its own accord for a reader its control plane did not name, and Flume's answer is the confirm's. (Record 0002 as amended on 2026-11-09, accepted by the user that day.)

### What goes back

- **[core.11]** What the runner carries back of a tool is the tool's own answer, each field as the tool gave it, or a reference to it: no repository content, task log, raw material or terminal byte is carried in a report, written to the runner's data or its log, or kept.
- **[core.26]** What goes over one account's connection names only that account's own repositories, leases, places and commands.
- **[core.49]** No drive's backlog, slow answer, refusal or failure delays another drive's launches, acts or reports; what drives share on a host is a cap or a synchronization its owner designs.
- **[core.27]** To a hosted control plane, the runner carries of a tool's status only the fields the protocol's copy of it names, each as the tool printed it, and leaves out the rest.
- **[core.28]** Nothing leaves a host from the runner but its control plane's protocol, git's calls, the calls to the forge's API that mint a token from the App's key it holds (core.33) and an OTLP export to a collector the host's configuration names, and what goes as health holds only ids, names, statuses, times, counts and digests.
- **[core.54]** Every launch that names a recipient names the runner one more, `boomdrive`, so Flume owes the runner each end of the place and holds the place's record past its tidy while one is owed; the runner carries each end in the place's status, and confirms it to Flume, as that recipient by the end's delivery key, only once its control plane has taken a report that holds it, so a control plane reads every end of the place from the runner's report, whatever tidied the place, and losing the runner's report loses no end. (Record 0030 as amended on 2026-11-09, accepted by the user that day.)

### Terminals

- **[core.29]** The runner reaches an agent's terminal only through Flume's command line, and no code of the runner's names a multiplexer or runs one's command line but setup's link of the set's herdr plugins by herdr's own command (record 0009 as amended 2026-11-11).
- **[core.30]** A terminal leaves the host only encrypted end to end to the browser that opened it: the runner makes a key pair for each terminal and signs its share with the host's key, takes the browser's share only when a key certified to a member signed it, and never sends a pane's bytes in the clear.

### Identity and credentials

- **[core.4]** No token, key or credential is in the repository: none is committed, none is a default in code, configuration or tests, and the runner reads each from the host when it runs.
- **[core.31]** A host's identity with a hosted control plane is a key pair the runner makes on the host, whose private key never leaves it, and every connection proves the key is held.
- **[core.32]** The host's key is kept only in the host's own credential store, the macOS keychain or an encrypted systemd credential, and never in a file readable in the clear.
- **[core.33]** Under a hosted control plane, no forge App's key or id is on a host for the runner or a tool to mint with: a host's forge calls use short-lived tokens the control plane sends down the runner's own connection, each for a repository of a drive the host serves. Under any other control plane, the runner alone holds the Boomdrive App's key, named by a path in its settings outside the Nix store, and mints those tokens itself. Every tool on a Boomdrive host takes its token from `boomdrive forge-token`, which speaks git's credential-helper protocol and gives one only for a served repository, on standard output alone. (Record 0007 as amended on 2026-11-09.)
- **[core.34]** The runner changes a repository only through the host's own `git` command, and a library may only read.
- **[core.58]** No try of a git call to a remote, the runner's own, a clone's fetch or a state repository's listing, or weir-branch's for crew's implementation, a state repository's fetch, listing or push, runs past thirty seconds, the limit agentplot/sluice record 0109 sets for the family: it runs in a process group of its own, which at the limit is asked to end, given two seconds, then killed, and it fails naming its command, its remote and the limit; weir's crate `weir-bounded`, at weir's `9cba691` or later, holds the limit, the halt and the ending, every such call takes them, and no crate of the runner's own holds a copy; a stop of the runner ends each such try in flight as its limit would, through `weir-bounded`'s halt, and begins none. (Record 0042 as amended on 2026-11-11 and 2026-11-12; weir record 0008 as amended 2026-11-12.)

### The runner's own files

- **[core.35]** The data directory holds only the lock, the clones, the runner's report, a launch's brief while Flume reads it and each implementation's caches, and everything in it but the report is made again from origin, Flume and the control plane.
- **[core.36]** A release that drops, renames or changes the meaning of a field the release before it read in a file the runner keeps names in its release notes the move each host makes by hand before it runs it, and reads nothing under the old name; a file the runner cannot read makes it refuse to start. (Record 0035.)

### Releases and installs

- **[core.37]** An install or an upgrade runs a release of the runner, or of a tool it brings, only once it has verified the release's provenance against the identity of the workflow that built it, and a failed check keeps what runs.
- **[core.38]** Each release names the least version of each tool it runs with and the versions it was checked against, and below a floor the runner takes no work that needs the tool and keeps its repositories.
- **[core.48]** A release's version is the one git-cliff makes under `cliff.toml` from the Conventional Commits since the newest release tag by version, and is written into the tree only by its release commit, cut from the commit of `main` that was pushed, which its tag `v<version>` names and which writes it into every file that carries Boomdrive's version, so a build from the tag reports it; `main`'s tree names `0.0.0`; the gate holds every commit since that tag to the convention, a commit that changes only the site, `site/` and its workflow `pages`, is in no release's notes and bumps no version, and the release workflow builds and publishes no binary, which core.37 and core.47 place. (Record 0024 as amended on 2026-11-11, proposed.)

### The flake

- **[core.44]** The flake's package set is the runner at this tree and each other tool of the host's at a release tag, each a derivation of the source the flake's lock names by its hash, reporting its tag's version, and taken from the tool's own flake where it publishes one.
- **[core.45]** The set the flake names is one the runner's tests pass with in the gate, running the set's own binaries, and a tool's tag moves only with the lock, in a change the gate passes.
- **[core.46]** Each tool's module writes that tool's file from one option per key, each named as the file names it, and the Boomdrive module sets the other tools' module options and writes no file of theirs; the flake's modules run the runner as the user's service reading that file, started only once the host's Nix store is mounted; no option, file or store path they make holds a token, a key or a credential, and enrollment stays a command run on the host.
- **[core.47]** The set reaches a host as binaries from the family's cache, which the flake's `nixConfig` names with its key: this repository's workflow alone pushes to it, from `main` or a release tag cut from it, the outputs of the flake's own derivations for every system the flake gives; a host substitutes them only where its own nix trusts the cache, and builds the same paths from source where it does not.
- **[core.57]** Where a tool's setting is a fact the set knows, from the host's accounts, the runner's settings, or the runner's own layout or another tool's of the set, the Boomdrive module gives it through that tool's module option: crew's kept repositories, each with the runner's clone as its `dir` and the runner's view as its `checkout`, and, where crew's module is on, crew's source of kinds to Flume, naming the roles file crew writes and its kinds folder; the runner's data folder is the modules' read-only `dataDir`, by the runner's own rule from its job's own environment, which whatever names the folder reads, and each kept repository's clone folder is their read-only `cloneDirs`, by the runner's own rule under that folder, which whatever names a clone's folder reads. A host writes such a value nowhere, and gives through a tool's own settings only what is its own. (Record 0036 as amended twice on 2026-11-11; record 0034, point 2.)

### Output

- **[core.39]** Every command of the runner's that answers takes `--json`, whose form within a version only ever gains fields; a refusal is `{"refused":{"refusal":{"reason":…}}}` on standard output; and it exits 0 answered, 1 refused and 2 for a usage error or a host that must be fixed.
- **[core.40]** Each line the running runner writes starts with its time, RFC 3339 in UTC to the second, then its subject and its words.

### Names

- **[core.12]** Every configuration key and every type names what it holds to its reader: a duration's key ends in `_interval`, a path's in `_root`, `_dir` or `_file`, and no key or type takes a word another tool uses for something else.

### The repository

- **[core.6]** Nothing commercial, no pricing, tier or customer, appears in this repository.
- **[core.41]** No text of a private repository is copied into this one, and no host, drive, state repository, person's path or account of anyone's is in its code, tests, fixtures or docs, but our own fleet's drives and machines where the site's measurement and field-note pages name them as ours (site.7).

### The gate

- **[core.7]** Every file the tree tracks is owned by a formatter the gate runs, or is excluded by name with its reason; every crate, the flake and the site is a moon project of its own, listed in `.moon/workspace.yml` with its language declared, whose check-fast tasks format, lint, type-check and test it, one task per check.
- **[core.8]** Every tool a gate task runs is the version the tree pins, on every host that runs the gate.
